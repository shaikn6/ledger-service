# Benchmarks

Load generated by [`loadtest/`](loadtest/) — concurrent `POST /v1/transfers`
against random account pairs, with a balance-conservation check after every run.

**Environment (not production hardware):** Apple M2 Pro (10 cores, 16 GB),
macOS · Go 1.27.2 · Postgres 16 (`postgres:16-alpine`, `max_connections=200`,
otherwise default settings) in Docker Desktop 29.7.2 · a single `ledger-service`
instance, `DB_MAX_CONNS=40` · loopback network · load generator on the same
machine. Real RDS/Aurora on dedicated hardware with connection pooling will
differ; treat these as a laptop floor, not a production figure.

Measured on 2026-10-19. Each scenario was run 3 times for 15 s
(`go run ./loadtest -accounts N -workers W -duration 15s`) against a fresh
database; the table gives the median, with the min-max across the 3 runs in
brackets. Throughput is posted transfers per second (`posted ... tx/s` in the
loadtest output). Run-to-run spread on a laptop is large, so the range matters
more than the median.

## Transfer throughput (the hard path — 1 tx, 2 ordered row locks, 7 statements)

| Scenario | Accounts | Workers | Throughput (median, range) | p50 | p99 | Errors | Balance |
|----------|:-------:|:------:|:--------------------------:|:---:|:---:|:------:|:-------:|
| Baseline | 50 | 8 | **1,455 tx/s** (1,398-1,519) | 4.6-4.8 ms | 12-16 ms | 0 | conserved |
| Sustained, hot accounts | 50 | 64 | **1,806 tx/s** (1,485-1,825) | 26-31 ms | 147-204 ms | 0 | conserved |
| Wide spread | 500 | 32 | **2,315 tx/s** (2,248-2,396) | 12.0-12.5 ms | 31-43 ms | 0 | conserved |
| High concurrency | 500 | 128 | **2,408 tx/s** (2,245-2,950) | 41.7-49.9 ms | 84-164 ms | 0 | conserved |

12 runs, ~365,000 transfers (including account funding) — **zero errors, zero
balance drift**, and `postings` stayed at exactly `2 × transfers` (729,930
rows for 364,965 transfers; double-entry invariant holds at the data layer
under load).

An earlier version of this file reported 2,735-2,757 tx/s for the two
500-account scenarios from an unrecorded run. The committed harness does not
reproduce that on this machine: the best single run was 2,950 tx/s but the
medians are 2,315-2,408 tx/s, so the README headline now uses the measured
figure.

## What the numbers say

- **Contention-bound.** 50 hot accounts plateau near 1,500-1,800 tx/s on
  row-lock contention; spreading to 500 accounts lifts the ceiling to roughly
  2,300-2,400 tx/s (median). Past ~32 workers for 500 accounts, more
  concurrency mostly adds queue latency: median throughput barely moves
  (2,315 to 2,408) while p50 latency roughly quadruples. This was not profiled
  to separate Postgres from the Docker VM and loadtest client sharing the
  same CPUs.
- **Correctness never degrades under load.** Every run conserves total balance
  to the cent; the ordered `SELECT … FOR UPDATE` + serialization-failure retry
  does its job. No lost updates, no double-spend, no deadlocks.
- **Lean footprint.** After the full run the service sat at **12 goroutines,
  ~8.8 MB heap, ~42 MB RSS** (`go_goroutines`, `go_memstats_heap_alloc_bytes`
  from `/metrics`, RSS from `ps`).

## Scaling levers (not yet applied)

Horizontal: the service is stateless — run N replicas behind a load balancer.
Vertical: Aurora writer + `pgbouncer`, partition `postings` by month, move
reads to replicas. Reads (`GET` account / transfer / postings) don't lock and
run several times faster than writes.

## Reproduce

```bash
make dev-db
DATABASE_URL='postgres://postgres:pg@localhost:55432/ledger?sslmode=disable' \
  DB_MAX_CONNS=40 go run ./cmd/ledger &
make bench   # go run ./loadtest -accounts 500 -workers 32 -duration 15s
```

`make bench` runs the "Wide spread" scenario. For the other rows, pass the
table's values as `-accounts` and `-workers` (other flags: `-addr`,
`-duration`, `-amount`, `-seed`; see `go run ./loadtest -h`).
