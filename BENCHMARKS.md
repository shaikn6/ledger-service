# Benchmarks

Load generated by [`loadtest/`](loadtest/) — concurrent `POST /v1/transfers`
against random account pairs, with a balance-conservation check after every run.

**Environment (not production hardware):** Apple M-series laptop, 10 cores ·
Postgres 16 in Docker (`max_connections=200`) · a single `ledger-service`
instance, `DB_MAX_CONNS=40` · loopback network. Real RDS/Aurora on dedicated
hardware with connection pooling goes materially higher; these are a laptop
floor.

## Transfer throughput (the hard path — 1 tx, 2 ordered row locks, 7 statements)

| Scenario | Accounts | Workers | Throughput | p50 | p99 | max | Errors | Balance |
|----------|:-------:|:------:|:----------:|:---:|:---:|:---:|:------:|:-------:|
| Baseline | 50 | 8 | **1,608 tx/s** | 4.4 ms | 11 ms | 25 ms | 0 | conserved |
| Sustained, hot accounts | 50 | 64 | **1,770 tx/s** | 26 ms | 172 ms | 611 ms | 0 | conserved |
| Wide spread | 500 | 32 | **2,735 tx/s** | 11 ms | 23 ms | 52 ms | 0 | conserved |
| High concurrency | 500 | 128 | **2,757 tx/s** | 44 ms | 99 ms | 204 ms | 0 | conserved |

~**175,000 transfers** across all runs — **zero errors, zero balance drift**,
and `postings` stayed at exactly `2 × transfers` (double-entry invariant holds
at the data layer under load).

## What the numbers say

- **Contention-bound, not CPU-bound.** 50 hot accounts plateau near 1,800 tx/s
  on row-lock contention; spreading to 500 accounts lifts the ceiling to
  ~2,750 tx/s. Past the knee (~32 workers for 500 accounts) more concurrency
  only adds queue latency — throughput is flat.
- **Correctness never degrades under load.** Every run conserves total balance
  to the cent; the ordered `SELECT … FOR UPDATE` + serialization-failure retry
  does its job. No lost updates, no double-spend, no deadlocks.
- **Lean footprint.** After the full run the service sits at **12 goroutines,
  ~12 MB heap, ~38 MB RSS** — it is the database, not the service, that is the
  scaling variable.

## Scaling levers (not yet applied)

Horizontal: the service is stateless — run N replicas behind a load balancer.
Vertical: Aurora writer + `pgbouncer`, partition `postings` by month, move
reads to replicas. Reads (`GET` account / transfer / postings) don't lock and
run several times faster than writes.

## Reproduce

```bash
make dev-db
DATABASE_URL='postgres://postgres:pg@localhost:55432/ledger?sslmode=disable' \
  DB_MAX_CONNS=40 go run ./cmd/ledger &
go run ./loadtest -accounts 500 -workers 32 -duration 15s
```
